# OpenClaw 记忆管理，从入门到高阶完整实战指南

**作者**: Ray Wang @wangray (@@wangray)
**时间**: 2026-02-02 11:39
**来源**: [原始链接](https://x.com/wangray/status/2027034737311907870)

---

一份从零到生产的实战指南，基于 5 个 Agent 协作团队 30 天的实际运行经验。

记忆迭代路线图：

第一部分：为什么 Agent 需要记忆系统

1.1 Context Window 不是记忆
每个 LLM Agent 都有一个致命弱点：上下文窗口（Context Window）不等于记忆。
上下文窗口是临时的。当对话过长，系统会自动压缩（Compaction），丢弃早期内容。当 session 结束，一切归零。Agent 醒来时，对之前发生的事情一无所知——除非它写进了文件。

Session 1: 做了重要决策 A → 没写进文件 → Compaction
Session 2: Agent 完全不知道决策 A 的存在 → 重复讨论 → 浪费时间

这不是理论问题。在实际运行中，我们观察到：
- Agent 在不同 session 中重复提出相同建议
- 跨频道（Telegram、Discord）的信息完全隔离
- Compaction 后 Agent 丢失了关键上下文

1.2 设计哲学
我们的核心原则只有一条：
文件 = 事实来源。你不写进文件的东西 = 你从来不知道的东西。

Agent 的记忆不在它的"脑子"里，而在磁盘上。Context window 是工作台，文件才是仓库。

这意味着：
- 所有重要信息必须实时写入文件
- Agent 每次启动都从文件读取状态
- 不依赖"记得去检查"，而是靠系统触发（cron、heartbeat）

1.3 本方案的定位
我们选择了 Markdown 文件作为记忆的主要载体，而不是纯数据库方案。

| 维度       | Markdown 文件               | 纯数据库     |
| ---------- | --------------------------- | ------------ |
| 可解释性   | 人类可直接阅读和编辑        | 需要查询工具 |
| 调试难度   | 打开文件就能看              | 需要 SQL/API |
| 版本控制   | git 天然支持                | 需要额外方案 |
| Agent 读写 | 原生支持（Read/Write 工具） | 需要额外集成 |
| 检索效率   | 较低（需要辅助索引）        | 较高         |

我们的答案是混合方案：Markdown 作为事实来源（可读层），QMD 向量数据库作为检索加速层。

第二部分：三层架构

2.1 短期层：NOW.md
用途： Agent 的"工作台"，记录当前状态、优先级、阻塞项。
特点：
- 每次 heartbeat 覆写（Write），不追加
- 只保留当天的完成项
- 是 Compaction 的"救生筏"——Agent 压缩上下文后首先读这个文件

关键设计： NOW.md 是唯一允许覆写的记忆文件。其他记忆文件只追加，不覆写。

2.2 中期层：每日日志
用途： 事件流水，记录当天发生的一切。是记忆系统的"原始数据"。
文件名格式： memory/YYYY-MM-DD.md

关键设计：
- 追加式（append-only），永不覆写
- 不同 session 看不到彼此的对话，所以重要信息必须立刻写进日志
- 格式统一为 ### HH:MM — Title，便于扫描和检索

2.3 长期层：INDEX.md → 结构化子目录
用途： 经过提炼的、结构化的知识库。不是原始事件，而是从事件中抽取的可复用知识。

INDEX.md 包含健康度指标（优先级、状态、最后验证日期），Agent 扫描时能立即判断哪些知识可信：
- 🔴 优先级的文件 = 核心知识，永不归档
- [⚠️ stale] 标记 = 超过 30 天未验证，信息可能过时

2.4 三层之间的信息流动
信息从上到下逐层提炼：
- 原始对话 → 写入日志（保留细节）
- 日志 → 提炼到知识库（抽取可复用的教训/决策/画像）
- 过期数据 → 归档到冷存储（释放检索空间）

第三部分：目录结构与文件规范

完整目录树：
workspace/
├── NOW.md                  # 短期：状态仪表盘（覆写式）
├── MEMORY.md               # 可选：指向 INDEX.md 的指针
├── AGENTS.md               # Agent 操作手册
├── HEARTBEAT.md            # Heartbeat 执行流程
│
└── memory/
    ├── INDEX.md            # 知识导航（启动时必读）
    ├── YYYY-MM-DD.md       # 每日日志（追加式）
    │
    ├── decisions/          # 战略决策记录
    ├── lessons/            # 可复用教训（按主题）
    ├── people/             # 人物/Agent 画像
    ├── projects/           # 项目状态追踪
    ├── preferences/        # 用户偏好与边界
    ├── reflections/        # 每日自省记录
    # 任务生命周期 ├── actions/           
    │   ├── open/
    │   ├── in-progress/
    │   └── done/           # >14 天自动归档
    │
    └── .archive/           # 冷数据（以 . 开头，搜索引擎不索引）

第四部分：写入机制

4.1 写入工具清单

memlog.sh — 日志写入脚本：
- 自动时间戳从系统时间获取，不需要 Agent 自己编码（避免幻觉）
- 追加式写入，永远不会覆盖已有内容

路由规则：
- 新信息到来
  ├─ 是一个重大决策？ → decisions/YYYY-MM-DD-slug.md (新建)
  ├─ 是一条可复用的经验？ → lessons/TOPIC.md (追加)
  ├─ 是关于某个人的新信息？ → people/NAME.md (追加)
  ├─ 以上都不是，但值得记录？ → memory/YYYY-MM-DD.md (日志)
  └─ 无实质内容 → 不写 (NOOP)

经验法则： 日志可以随便写（宁多勿少），但知识文件要谨慎写（先读再写）。

4.2 CRUD 验证
写入知识文件（lessons/、people/、decisions/）时，必须遵循"先读再写"原则：
- 已有内容完全覆盖了新知识 → NOOP (跳过)
- 新知识是对已有内容的更新 → UPDATE（旧版标记: > [Superseded]）
- 新知识与已有内容矛盾 → CONFLICT（两版都保留，加标记）
- 全新的知识 → ADD (追加新段落)

为什么需要 CRUD 验证？
不做验证的后果是记忆幻觉——Agent 写入了错误的、重复的、或矛盾的信息。

第五部分：检索机制

5.1 三级检索策略

L1: 扫 INDEX.md → 定位目标文件 (0 cost, 纯文件读取)
L2: 直接读取目标文件 (0 cost, 纯文件读取)
L3: QMD 语义搜索 (有延迟, 适合模糊查询)

优先走 L1/L2，L3 作为兜底。

5.2 QMD 混合检索
QMD 是一个本地混合搜索引擎，结合了两种检索方式：
- BM25 关键词：精确匹配快（~0.15s），不理解语义
- 向量语义：理解语义相似度，较慢（~12s）

第六部分：记忆生命周期

6.1 日间：实时写入
- Agent 在日间通过 heartbeat（定时心跳）和用户对话两个途径写入记忆

6.2 每晚 23:30：日志同步
日志同步是当天的最后一道防线，确保没有信息遗漏。

6.3 每晚 23:45：夜间反思
夜间反思是记忆系统最核心的整合环节，相当于人脑睡眠时的记忆整合（Consolidation）。

执行流程：
1. 读取上下文（今日日志、NOW.md、相关 lessons/ 文件）
2. 写反思（计划 vs 实际、什么做对了、什么做错了、学到了什么）
3. 清理日志
4. CRUD 回写知识库 ← 核心步骤
5. 过时扫描

6.4 每周日 00:00：冷数据归档
每周一次的 GC（Garbage Collection）负责把冷数据归档到 .archive/。

第七部分：遗忘与衰减

7.1 为什么需要主动遗忘
人脑的艾宾浩斯遗忘曲线告诉我们：遗忘不是 bug，是 feature。它让大脑保持高效检索的能力。

7.2 温度模型
用"温度"（Temperature）来衡量一条记忆的活跃程度：
- T > 0.7: 🔥 Hot - 保持在活跃索引
- 0.3 < T ≤ 0.7: 🌤️ Warm - 保留但检索降权
- T ≤ 0.3: 🧊 Cold - 移至 .archive/

7.3 归档规则
- 日志 >30 天 + 近 7 天无引用 → 归档
- 反思 >30 天 → 归档
- decisions/、lessons/(🔴)、people/ → 永不归档

---

第八部分：可靠性保障

8.1 记忆幻觉问题
Agent 的记忆系统面临四种"幻觉"风险：
- 编造：写入从未发生过的事情
- 错误：写入不准确的信息
- 冲突：同一事实的两个矛盾版本并存
- 遗漏：重要信息没有被记录

8.2 写入时验证：CRUD 四分类
- 无关 → ADD
- 相似且一致 → NOOP
- 相似但不同 → UPDATE
- 矛盾 → CONFLICT

8.3 过时检测
每个知识文件的 frontmatter 中有 last_verified 字段。夜间反思时扫描所有文件，超过 30 天未验证 → 标记 [⚠️ STALE]。

---

第九部分：多 Agent 协作中的记忆

9.1 每个 Agent 独立 memory/ 目录
在多 Agent 架构中，每个 Agent 有自己的工作空间和记忆目录。

设计原则： 每个 Agent 只读写自己的 memory/ 目录。跨 Agent 信息共享通过主 Agent 的 heartbeat 聚合。

9.2 跨 Session 信息同步原则
LLM Agent 的一个关键约束：不同 session 之间完全隔离。
解决方案： 文件是唯一的跨 session 通道。

---

第十部分：快速上手

10.1 最小可用配置
最少需要 3 个文件：
- NOW.md — 状态板
- AGENTS.md — Agent 操作手册（含记忆规则）
- memory/YYYY-MM-DD.md — 每日日志

10.2 渐进式搭建路径
- 阶段 0（立刻）：NOW.md + AGENTS.md + 每日日志
- 阶段 1（第 1 周）：增加 INDEX.md + lessons/ + decisions/
- 阶段 2（第 2 周）：增加 Frontmatter 规范 + 夜间反思 cron
- 阶段 3（第 3 周）：增加 QMD 语义搜索 + 冷数据归档
- 阶段 4（第 4 周+）：多 Agent 协作记忆

建议：不要一次性搭全。从阶段 0 开始，每周加一层。

---

附录：设计灵感
本记忆系统的设计借鉴了多个来源：
- 人脑记忆整合：短→中→长期分层；睡眠时整合
- 艾宾浩斯遗忘曲线：时间衰减模型；主动遗忘保持效率
- Stanford Generative Agents：recency × importance × relevance 三维检索评分
- Mem0：ADD/UPDATE/DELETE/NOOP 自适应 CRUD
- MemGPT：虚拟内存概念；核心记忆 vs 归档记忆
- HaluMem：记忆幻觉分类；写入验证的必要性

这套系统从一个只有 3 个文件的最小配置起步，经过 30 天的实际运行迭代到了当前状态。
