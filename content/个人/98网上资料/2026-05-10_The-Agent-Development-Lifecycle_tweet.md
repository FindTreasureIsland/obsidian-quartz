# The Agent Development Lifecycle

**来源**：https://x.com/i/status/2053157547985834227

**作者**：Harrison Chase（LangChain CEO）

**发布时间**：2026-05-10

---

## 核心框架

Agent 开发生命周期有四个部分：

```
Build → Test → Deploy → Monitor → Iterate
```

顺序是刻意设计的。测试应该在 agent 进入生产环境之前开始，而不是之后。团队需要在部署前测试 agent，以受控方式部署，监控它们在生产中的行为，并将这些学习反馈到下一个构建和评估循环中。

---

## Build

构建阶段决定创建什么类型的 agent 系统以及想要使用什么级别的抽象。

### 工具分层

| 类型 | 说明 | 代表 |
|------|------|------|
| **Agent frameworks** | 抽象层，帮助开发者组合模型调用、工具、提示词、检索、结构化输出和 agent 循环 | LangChain, CrewAI |
| **Agent runtimes** | 执行层，支持需要状态、流程控制、持久性和人工干预的 agent | LangGraph |
| **Agent harnesses** | 做事的周边结构：提示词、skills、MCP servers、hooks、中间件，有时还有文件系统 | Deep Agents, Claude Agent SDK |

### No-code / Low-code

- LangSmith Fleet、Claude Cowork、n8n 让更多人参与 agent 开发
- 但 no-code 工具不消除工程控制的需要
- Hooks 和中间件特别重要，允许团队在工具调用、上下文处理、审批、认证或业务规则周围添加自定义逻辑，而不需要从头重建每个 agent

**最好的构建环境**：简单的事简单做，复杂的事也有可能。让领域专家编辑提示词、skills 和上下文，同时给工程师控制需要可靠、可测试、可治理的部分。

---

## Test

在 agent 部署之前，团队需要一种方式来判断它是否真的准备好了。

### 数据集和指标

数据集是团队保存学习成果的方式。没有它们，相同的失败会在提示词更改、模型升级或工具更新后重新出现。

指标取决于任务：
- **有明确标准答案的**：正确性直接衡量（提取了正确的值、选择了正确的标签、更新了正确的字段）
- **没有单一标准答案的**：基于标准的评估——响应是否有依据、是否遵循了策略、是否要求了澄清、是否高效完成任务而没有不必要的工具调用

### 实验

实验将数据集和指标连接到迭代。允许团队在相同的评估集上比较提示词、模型、检索策略、工具模式和编排模式。

目标不是第一天就创建一个完美的评估套件，而是从一个有用的开始，然后持续改进。最有价值的评估数据集是从最难的例子中构建的：首先来自开发和 dogfooding，然后来自生产。

### 模拟

许多 agent 是多轮系统。它们不只是回答一个问题，而是进行对话、收集信息、调用工具、更新状态、从歧义中恢复。对于这些 agent，单轮评估是不够的。

例子：
- 支持 agent 可能需要处理愤怒的客户、问后续问题、检查订单状态、决定是否需要升级
- 编码 agent 可能需要检查仓库、做更改、运行测试、响应反馈
- 内部运营 agent 可能需要在采取行动之前收集缺失的信息

## Deploy

一旦 agent 被构建和评估，它需要一个可以可靠运行的环境。

### Agent Runtime

生产 agent runtime 通常需要支持：
- **持久执行** — agent 可以检查点进度并在失败时恢复，而不是丢失工作
- **Human-in-the-loop** — agent 可以在需要批准、澄清或审查时暂停

解决方案：LangSmith Deployment、AWS AgentCore，或者基于 Temporal 构建自己的 runtime

### Sandboxes

许多 agent 需要专用执行环境（写代码、执行代码、检查文件、转换文档、与文件系统交互）。Sandbox 提供隔离的执行环境，同时减少错误或不安全行为的爆炸半径。

例子：LangSmith Sandboxes、Daytona、E2B

不是每个 agent 都需要完整的 sandbox。有时候只需要一个地方来存储和检索文件。虚拟文件系统就够了。

### Context Hub

部署中经常被忽视的部分是管理提示词和上下文。

agent 最重要的部分可能不是传统应用程序代码。提示词、检索上下文、skills 和任务说明可能比应用程序本身更需要频繁更改。它们也需要由非工程师编辑。

这创建了对提示词或上下文 hub 的需求：一个存储、版本控制、审查和更新 agent 非代码部分的地方。这允许团队在不进行全面部署的情况下调整 agent 行为，并让领域专家拥有他们最了解的部分。

---

## Monitor

部署 agent 后，团队需要了解它们在生产中的实际行为。

### 与传统软件监控的区别

agent 可以返回技术成功响应但仍然任务失败。它可能调用了错误的工具、依赖了错误的上下文、跳过了需要的审批步骤，或者产生了听起来合理但错误的答案。

### Traces

Trace 捕获 agent 的完整轨迹：收到的输入、进行的模型调用、调用的工具、收到的输出，以及产生的最终响应或操作。这是理解 agent 实际做了什么所需的细节级别。

**Agent observability powers agent evaluation**。如果看不到轨迹，就不能可靠地调试行为或将这些失败转化为未来的评估。

### 信号

监控还应包括从这些 traces 中收获信号：
- LLM-as-judge 评估器可以评分 agent 是否回答了用户的问题、是否遵循了策略、是否使用了正确的语气
- 更简单的：regex 可以捕获是否出现了必需的短语、是否调用了禁止的工具、是否发生了已知的失败模式

### 反馈

只存储 traces 是不够的。团队还需要将这些反馈与 traces 一起存储。反馈可以来自 LLM judges、regex 信号、人工审查或直接的用户反馈。

### Dashboard

有用的 agent dashboard 跟踪：使用量、反馈、延迟、成本、工具调用、评估器分数和反复失败模式。警报应在重要阈值被跨越时触发：延迟上升、成本增加、工具失败、用户反馈下降或策略违规激增。

## Iterate

最佳组织快速而系统地完成 agent 开发生命周期。

不是等到完美的 agent 才发货。相反：构建有用的东西，充分测试以了解其行为，以受控方式部署，监控它在生产中的表现，并将所学反馈到下一个版本。

这不是草率发货。关键是拥有可见性。

拥有数据集、实验、tracing、反馈和 dashboard 的团队可以直接从真实使用中学习。他们可以在广泛推广之前测试更改，识别生产中什么坏了，将失败转化为评估，并在不依赖猜测的情况下改进 agent。

**这就是团队如何爬坡，agent 系统如何随时间改进。**

---

## Govern

治理围绕整个 agent 开发生命周期。

对于单个 agent，轻量级控制可能就足够了。随着组织部署更多 agent，治理变得必要。没有它，团队很快就会遇到难以发现、难以监控、成本高昂、职责不清的 agent。

### 成本

Agent 可能很昂贵，因为涉及多个模型调用、长上下文窗口、重复的工具使用、重试或长时间运行。组织需要通过预算、使用监控、警报以及了解哪些 agent、团队、模型或工具在推动成本来管理和跟踪支出。

### 工具访问

Agent 有用是因为它们可以采取行动，但这也引入了风险。团队需要清楚的控制，了解哪些工具是 agent 可以访问的、在什么条件下、代表哪些用户。

这涉及：
- **审计追踪**：如果 agent 调用工具，组织应该能够检查哪个 agent 进行了调用、使用了什么输入、产生了什么输出、什么用户或策略授权了该操作
- **Human-in-the-loop**：并非每个工具调用都应该完全自动化。有些操作应该暂停等待人工审查，特别是当它们涉及客户、财务系统、敏感数据或生产基础设施时

### 可发现性

随着组织构建更多 agent，他们也积累了更多可重用资产：提示词、skills、工具、检索源、策略，甚至其他 agent。没有好的发现和治理机制，团队倾向于反复重新创建这些组件，导致不一致。

这对于 skills 尤为重要。一个 skill 可以编码工作流、写作风格、特定领域的过程或使用工具的说明。如果一个团队已经构建了一个好的 skill，另一个团队应该能够找到它，而不是从头开始写一个新版本。

---

## 结论

最佳组织已经开始以这种方式运作。他们早发货，但不盲目发货。他们在部署前评估，在部署后监控行为，并持续使用所学知识使下一个版本变得更好。

这就是让 agent 开发变得可重复的原因。这也是允许 agent 从演示进入可靠生产系统的原因。
