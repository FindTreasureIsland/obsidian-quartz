# Codex Best Practices

## 文章概述

如果你刚接触 Codex 或 AI 编程助手，本指南将帮助你更快获得更好的结果。它涵盖了使 Codex 在 CLI、IDE 扩展和 Codex 应用中更有效的核心习惯，从提示词编写、规划到验证、MCP、技能和自动化。

**核心理念：** 把 Codex 当作一个需要配置和改进的团队成员，而不是一次性的助手。

---

## 一、起始：上下文和提示词

### 1.1 上下文是关键

Codex 已经足够强大，即使提示词不完美也能提供帮助。但清晰的提示词确实能让结果更可靠，尤其是在更大的代码库或更高风险的任务中。

在大型或复杂的代码库中，最大的突破是给 Codex 正确的任务上下文和清晰的工作结构。

### 1.2 提示词的四个要素

在提示词中包含以下四个内容：

1. **任务上下文** — Codex 需要了解什么背景？
2. **明确的目标** — 你希望完成什么？
3. **约束条件** — 有什么限制或规范？
4. **验收标准** — 怎么才算"完成"？

这有助于 Codex 保持范围明确，减少假设，并产生更容易审查的工作成果。

### 1.3 规划模式

如果任务复杂、模糊或难以描述，请让 Codex 在开始编码之前先做规划。

**方式一：使用 Plan 模式**
Plan 模式让 Codex 收集上下文、提出澄清问题，并在实施前构建更强的计划。用 `/plan` 或 `Shift+Tab` 切换。

**方式二：让 Codex 做访谈**
如果你有一个粗略的想法但不确定如何描述，请让 Codex 先向你提问。告诉它挑战你的假设，在写代码之前把模糊的想法变成具体的东西。

**方式三：使用 PLANS.md 模板**
对于更高级的工作流，你可以配置 Codex 遵循 PLANS.md 或执行计划模板。

### 1.4 AGENTS.md：持久指导

一旦提示词模式有效，下一步就是停止手动重复。这就是 AGENTS.md 的用武之地。

AGENTS.md 相当于 Agent 的开放格式 README。它会自动加载到上下文中，是编码你和你的团队希望 Codex 如何工作的最佳位置。

**使用 `/init` 命令快速启动**
CLI 中的 `/init` 命令是在当前目录中搭建 starter AGENTS.md 的快速启动命令。

**多级配置**
- 全局 AGENTS.md：放在 `~/.codex`，作为个人默认设置
- 仓库级 AGENTS.md：定义共享标准
- 子目录级 AGENTS.md：用于本地规则

**保持实用**
- 短小准确的 AGENTS.md 比冗长的模糊规则更有用
- 从基础开始，只有在注意到重复错误时才添加新规则
- 如果 AGENTS.md 变得太大，把主要内容保持简洁，引用任务特定的 markdown 文件

**当 Codex 犯同样的错误两次时**：要求它做复盘并更新 AGENTS.md。指导保持实用且基于真实的摩擦点。

## 二、配置：让 Codex 更一致

### 2.1 config.toml

config.toml 是定义持久偏好的地方，如 MCP 服务器、配置文件、多代理设置和功能开关。

### 2.2 沙箱与权限

Codex 提供操作系统级沙箱，有两个关键控制：

- **Approval mode（审批模式）**：决定 Codex 何时需要你许可才能运行命令
- **Sandbox mode（沙箱模式）**：决定 Codex 是否可以读取或写入目录，以及可以访问哪些文件

**建议**：如果你刚接触编程代理，从默认权限开始。默认保持审批和沙箱严格，然后只在信任的仓库或特定工作流中根据需要放宽权限。

### 2.3 早期配置真实环境

许多质量问题实际上是配置问题：
- 错误的工作目录
- 缺少写入权限
- 错误的模型默认值
- 缺少工具和连接器

## 三、验证：不要停止于"做完了"

不要只问 Codex 做修改就结束了。要求它在需要时创建测试，运行相关检查，确认结果，并在接受工作之前审查。

Codex 可以为你做这个循环，但前提是它知道"好"是什么样子的。这个指导可以来自提示词或 AGENTS.md。

**在 Codex 应用中**：切换 diff 面板直接在本地审查更改。点击特定行提供反馈，作为下一个 Codex 回合的上下文。

**使用 `/review` 命令**
如果你和你的团队有 `code_review.md` 文件并在 AGENTS.md 中引用它，Codex 可以在审查时遵循该指导。这是团队希望审查行为在仓库和贡献者之间保持一致的强模式。

## 四、MCP：连接外部系统

当 Codex 需要的上下文存在于仓库外部时，使用 MCP（Model Context Protocol）。

MCP 是一个开放标准，用于将 Codex 连接到外部工具和系统。Codex 支持 STDIO 和 Streamable HTTP 服务器与 OAuth。

**在 Codex 应用中**：进入 Settings → MCP servers 查看自定义和推荐服务器。

**添加工具的原则**：
- 只在工具解锁真正的工作流时才添加
- 不要从一开始就连接你使用的每一个工具
- 从一到两个明显消除你经常手动循环的工具开始，然后再扩展

## 五、Skills：让重复工作自动化

### 5.1 什么时候用 Skills

一旦工作流变得可重复，停止依赖冗长的提示词或反复来回。使用 Skill 将指令打包在 SKILL.md 文件中，Codex 应该一致地应用上下文和支持逻辑。

**经验法则**：如果你不断重用相同的提示词或纠正相同的工作流，它应该成为一个 Skill。

### 5.2 Skills 特别有用的场景

- 定期的代码审查任务
- 文档更新
- 错误修复工作流
- 测试生成和运行
- 任何重复性任务

### 5.3 Skill 创建建议

- 保持每个 Skill 范围单一
- 从 2-3 个具体用例开始
- 定义清晰的输入和输出
- 写清楚描述，说明 Skill 做什么以及何时使用
- 不要试图在一开始就覆盖每一个边缘情况
- 从一个代表性任务开始，把它做好，然后把它变成 Skill 并改进

**提示**：使用 `$skill-creator` Skill 来搭建第一个版本。第一个版本保持本地，迭代完成后打包为插件。

### 5.4 个人技能 vs 团队技能

- 个人 Skills：存储在 `$HOME/.agents/skills`
- 共享团队 Skills：可以检入仓库的 `.agents/skills` 目录

## 六、Automations：让工作流定时运行

### 6.1 核心理念

技能定义方法，自动化定义时间表。如果工作流仍然需要很多指导，先把它变成 Skill。一旦它可预测了，自动化就成为力量倍增器。

### 6.2 使用 Automations 的场景

- 定期的代码审查任务
- 文档更新
- 错误修复工作流
- 测试生成和运行

### 6.3 建议

- 使用 Automations 进行反思和维护，而不仅仅是执行
- 审查最近的会话，总结重复的摩擦点，并随着时间改进提示词、指令或工作流设置

---

## 七、会话管理

Codex 会话不仅仅是聊天历史。它们是随着时间累积上下文、决策和工作的线程，所以管理好它们对质量有很大影响。

### 7.1 保持一个线程一个工作单元

如果工作仍然是同一问题的一部分，保持在同一线程通常更好，因为它保留了推理轨迹。只有在工作真正分支时才 fork。

### 7.2 使用子代理

使用 Codex 的子代理工作流将bounded 工作从主线程卸下。保持主 Agent 专注于核心问题，使用子代理处理探索、测试或分类等任务。

---

## 八、常见错误

1. **没有给足够的上下文**：不要假设 Codex 知道你的代码库
2. **不使用 Plan 模式**：复杂任务先规划
3. **不让 Codex 复盘**：错误重复发生时更新 AGENTS.md
4. **一次性连接太多工具**：从一个或两个开始
5. **不验证输出**：要求测试和审查
