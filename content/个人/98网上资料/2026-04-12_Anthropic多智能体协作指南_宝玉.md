## 核心内容

### 选型建议
从最简单的、能跑通的模式开始，观察它在哪里遇到瓶颈，然后再逐步升级。

### 五种模式

#### 1. 生成-验证者 (Generator-Verifier)
**最简单的多智能体模式，落地最广**

运作方式：
- Generator 接到任务后给出一版初步结果
- Verifier 评估是否符合标准
- 通过则输出，不通过则打回修改
- 循环直到满意或达到最大次数

适合场景：
- 代码生成（一个写代码，一个写测试）
- 事实核查
- 合规性审查
- 任何"一次错误代价远大于多跑一圈"的领域

局限：
- 验证者标准要具体明确
- 必须设最大循环次数，防止死循环

#### 2. 调度-子智能体 (Orchestrator-Subagent)
**层级制，有个主管**

运作方式：
- Orchestrator 负责规划工作、分发任务、汇总结果
- Subagent 负责具体分摊工作，做完向上汇报
- Claude Code 用的就是这种模式

适合场景：
- 代码审查（安全漏洞、测试覆盖、代码风格、架构一致性）
- 任务拆解清晰、互不依赖

局限：
- 调度者容易成信息瓶颈
- 子智能体串行干活

#### 3. 智能体团队 (Agent Teams)
**并行 + 长期记忆**

运作方式：
- Coordinator 创建多个长期存在的 Team members
- 成员从共享任务队列抢单
- 成员会积累领域知识，越干越熟练

适合场景：
- 代码库迁移（每个成员负责一个服务模块）
- 子任务独立、需长时间处理

局限：
- "独立"是生命线，也是软肋
- 需要冲突解决机制

#### 4. 消息总线 (Message Bus)
**发布-订阅模式**

运作方式：
- Agent 只发布和订阅"话题"
- Router 精准推送消息给相关Agent
- 新Agent加入只需订阅相应话题

适合场景：
- 安全运营系统（警报分诊）
- 事件驱动的流水线
- 智能体生态系统不断扩展

局限：
- 排查问题困难
- Router分错消息会静默崩溃

#### 5. 共享状态 (Shared State)
**去中心化，没有中间商**

运作方式：
- 所有Agent读写同一个持久化存储
- 像在公共黑板前工作
- 有新发现就写回，大家互相踩着肩膀往上爬

适合场景：
- 跨领域综合研究
- 需要消除单点故障

局限：
- 可能重复造轮子或南辕北辙
- 容易陷入"反应式死循环"

### 选型对照表

| 场景 | 推荐模式 |
|------|---------|
| 看中输出质量，有明确评估标准 | 生成-验证者 |
| 任务拆解清晰，短平快 | 调度-子智能体 |
| 子任务独立，需长时间运行 | 智能体团队 |
| 事件驱动流水线 | 消息总线 |
| 高度协作，需频繁共享发现 | 共享状态 |
| 不允许单点故障 | 共享状态 |

### 核心建议
从"调度-子智能体"开始，先跑起来，观察瓶颈，再根据具体痛点进化到其他模式。
