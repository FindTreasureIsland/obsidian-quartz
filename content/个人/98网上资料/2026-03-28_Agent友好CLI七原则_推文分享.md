## 文章正文

I've been building a couple of CLIs as side projects recently, and I wanted them to be agent-first from the start. Not "an agent could probably use this" but optimized for how agents work.

What I found was exactly what you'd expect: great CLI design resources that are entirely about humans. The Command Line Interface Guidelines project is excellent. But they're written for a world where the consumer is a person at a terminal who can read a prompt, make a judgment call, and visually parse a nicely formatted table. Agents can handle some of that when they're running interactively, but the moment an agent or skill spawns a background subagent, interactive CLIs break.

Colored output wastes tokens. Unbounded responses eat context windows. The assumptions baked into human-first CLI design create real failure modes for agent consumers.

Anthropic published solid guidance on writing tools for agents, but it's tool-design guidance broadly, not CLI-specific. What was missing was a practical rubric for evaluating whether a CLI works well for agents, not whether it technically works at all.

So I wrote one. Seven principles that cover the gap between "this works" and "this works well."

---

## Why CLI over MCP?

CLIs are text in, text out, composable by design. LLMs already know common CLI tools from training data, so there's zero schema overhead. An MCP server can burn tens of thousands of tokens just loading tool definitions before a single question gets asked.

MCP earns its complexity when you need per-user auth and structured governance, but for the tools developers build and use day-to-day, a well-designed CLI is faster, cheaper, and more reliable.

---

## A Severity Rubric

Each finding maps to one of three severity levels:

- **Blocker**: The issue prevents reliable agent use. The command hangs, requires human intervention, or produces output an agent can't recover from.
- **Friction**: Agents can use it, but inefficiently: more retries, wasted tokens, brittle parsing, extra tool calls.
- **Optimization**: The CLI works fine but could be faster, cheaper, or more reliable for agent consumers.

---

## Principle 1: Non-interactive by default

**The principle**: Any command an agent might automate should run without prompts.

This is the most common blocker. When a skill spawns a subagent that shells out to a CLI, there's no way to surface an interactive prompt back to the user. The command just hangs.

```bash
# Human at a terminal (TTY detected) — prompts fill in missing inputs
$ blog-cli publish
? Status? (use arrow keys)
    draft
  > published
    scheduled

# Agent or script (no TTY, or --no-input) — flags only, no prompts
$ blog-cli publish --content my-post.md --yes
Published "My Post" to personal (post_id: post_8k3m)
```

**The fix**: Support `--no-input` or `--non-interactive`, detect TTY vs non-TTY and suppress prompts, accept `--yes` / `--force` for confirmation bypass.

---

## Principle 2: Structured, parseable output

**The principle**: Commands that return data should expose a stable machine-readable representation.

Agents need data contracts, not presentation formatting. A nicely aligned table with ANSI colors is great for humans and useless for an agent trying to extract a post ID.

```bash
# Human-readable
$ blog-cli publish --content my-post.md
Published "My Post" to personal
URL: https://personal.blog.dev/my-post
Post ID: post_8k3m

# Machine-readable
$ blog-cli publish --content my-post.md --json
{"title":"My Post","url":"https://personal.blog.dev/my-post","post_id":"post_8k3m","status":"published"}
```

**What to implement**: Support `--json` on data-bearing commands, use exit code 0 for success and non-zero for failure, write result data to stdout and diagnostics to stderr.

---

## Principle 3: Fail fast with actionable errors

**The principle**: When a command fails, the error should teach the agent how to succeed on the next attempt.

Humans can infer what went wrong from a vague error message. Agents can't.

```bash
# Bad
$ blog-cli publish
Error: missing required arguments

# Better
$ blog-cli publish
Error: --content is required.
Usage: blog-cli publish --content <file> [--status <status>]
Available statuses: draft, published, scheduled
Example: blog-cli publish --content my-post.md
```

The good error does four things: names the specific problem, shows the correct invocation shape, suggests valid values, and includes an example.

---

## Principle 4: Safe retries and explicit mutation boundaries

**The principle**: Agents retry, resume, and sometimes replay commands. Mutating commands should make that safe when possible, and dangerous mutations should be explicit.

```bash
# Repeating the same command doesn't create duplicate work
$ blog-cli publish --content my-post.md
Published "My Post" to personal (post_id: post_8k3m)

$ blog-cli publish --content my-post.md
Already published "My Post" to personal, no changes (post_id: post_8k3m)

# Dangerous mutation is explicit
$ blog-cli posts delete --slug my-post --confirm
```

**The goal**: Make duplicate application a no-op or clearly detectable. Provide `--dry-run` for consequential mutations. Use explicit destructive flags.

---

## Principle 5: Progressive help discovery

**The principle**: Agents don't read a CLI's full documentation up front. They probe top-level help, then subcommand help, then examples. Help should support that incremental workflow.

```bash
$ blog-cli --help
Usage: blog-cli <command>

Commands:
  publish     Publish content
  posts       List and manage posts

$ blog-cli publish --help
Publish a markdown file to your blog.

Options:
  --content   Path to markdown file
  --status    Post status (draft, published, scheduled; default: published)
  --yes       Skip confirmation prompt
  --json      Output as JSON
  --dry-run   Preview without publishing

Examples:
  blog-cli publish --content my-post.md
  blog-cli publish --content my-post.md --status draft
```

Each subcommand's help should include: a one-line purpose, a concrete invocation pattern, required arguments or flags, and the most important modifiers or safety flags.

---

## Principle 6: Composable and predictable structure

**The principle**: Agents solve tasks by chaining commands. They benefit from CLIs that accept stdin, produce clean stdout, and use predictable naming and subcommand patterns.

**What to implement**:
- Accept input via flags, files, or stdin where it helps automation
- Support `-` as a stdin/stdout alias when file paths are involved
- Keep command structures consistent across related resources
- Prefer flags for ambiguous multi-field operations

Consistency across subcommands is the subtle one. If `blog-cli posts list` supports `--json` but `blog-cli posts stats` doesn't, the agent has to learn the exception.

---

## Principle 7: Bounded, high-signal responses

**The principle**: Agents pay a real cost for every extra line of output. Large outputs are sometimes justified, but the CLI should make narrow, relevant responses the default.

```bash
# Broad but bounded
$ blog-cli posts list --limit 25
Showing 25 of 312 posts
To narrow results: blog-cli posts list --status published --since 7d --limit 10

# More precise
$ blog-cli posts list --tag javascript --status published --since 30d --limit 10 --json
```

The important design move: when the CLI truncates, it teaches the agent how to narrow the query.

**What to implement**:
- Support filtering, pagination, and limits on large result sets
- Provide concise vs detailed response modes
- Return summaries and identifiers before raw detail

---

## Humans ❤️ Agents

Every principle here makes a CLI better for humans too. Structured output, actionable errors, bounded responses, non-interactive automation paths: these aren't concessions to agents at the expense of human experience. They're good CLI design that we've been inconsistently applying.

Agents have gotten more forgiving with every model release. But "well enough" costs tokens, burns retries, and introduces failure modes that don't need to exist. Designing for agents as a first-class consumer removes that tax, and the CLI ends up better for humans in the process.
