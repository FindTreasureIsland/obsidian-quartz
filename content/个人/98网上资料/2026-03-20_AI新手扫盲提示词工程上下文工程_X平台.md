## 前言

回望 Agent 的应用史，本质上就是控制史。

LLM（Large Language Model，大语言模型）生成内容本质是个"概率游戏"。它的输出质量，在出生那一刻（预训练、微调、强化学习）就已经定型了。

这种随机性在完成某些确定性的任务时往往是很致命的。

为了对抗这种随机性，人们对 Agent 的控制行为贯穿 LLM 发展至今。往大的说是 Harness Engineering（控制工程），往小的说有本文提到的提示词工程和上下文工程。

---

## 提示词 vs 提示词工程

**提示词**：给 LLM 下的指令或提问。

**提示词工程**：本质上就是一套通过结构 + 信息 + 约束引导 LLM 输出期望回答的沟通艺术。我们可以通过定义角色、发布任务、给出约束条件等提示词来规范 LLM。

**底层原理**：Prompt 本质是在限制模型的概率分布空间。

### 经典提示词模板

```markdown
## 角色
你是程序员Left，AI Coding 高度使用者

## 背景
之前已经给小白讲了什么是 LLM、Chatbot、Agent

## 任务
现在要给小白讲什么是提示词工程和上下文工程

## 约束
要讲的小白也能懂的话，不要讲一大堆行业黑话
```

## 上下文基础概念

发送给 LLM 的内容（上下文）包含：
1. 用户提示词
2. 系统提示词
3. LLM 回答

上下文窗口：上下文的最大长度。

### 上下文太长怎么办？

1. 限制历史上下文长度
2. 当上下文快爆了的时候，压缩历史上下文

### 中间迷失（Lost In Middle）

LLM 的注意力并不是线性分布的：
- **首因效应**：开头的内容注意力最强
- **近因效应**：结尾的内容注意力最强
- **中间内容**：注意力大幅衰减

> 核心结论：在上下文工程中，"放在哪"往往比"放什么"更重要。

## 上下文工程

如果说提示词工程是告诉 LLM "应该怎么答"，那么上下文工程就直接给了 LLM 说明书，叫它学习说明书后做出回答。

### 第一招：遇到 LLM 不明白的知识，就在上下文中补充信息

## 进阶：上下文工程实践

### RAG（检索增强生成）

将读知识库分为两步：**预处理 + 检索**。

- 预处理：先将文档进行段落切分，再将段落生成索引
- 检索：根据待匹配的内容，搜索匹配的索引段落

典型应用：Google NotebookLM，支持最大 50 个源文件，外挂知识库实现超长上下文能力。

### Grep（精确匹配）

Claude Code 在 Coding 场景下发现：RAG 更擅长语义匹配，而代码检索往往需要精确匹配。因此 Claude Code 使用模式匹配（Grep）精确搜索，效果大幅提升。

### Skill（渐进式加载）

Skill 把加载拆成三步骤：
1. **加载元信息**：让 Agent 知道有这个技能
2. **加载 Skill.md**：Agent 需要用时才读取
3. **加载资源**：执行过程中才加载对应资源

### Todo（任务清单）

Goal Drifting（目标漂移）：Agent 执行到一半就不知道自己该干什么了。

Manus 的解法：在上下文中适时追加任务清单，利用近因效应，让任务清单始终在 LLM 视野范围内。

但随着 LLM 能力提升，追加任务清单的方式会限制 LLM 的灵活性。于是 Claude Code 将 Todo 做成了工具，实现跨 Agent 任务共享。

---

## 如何管理好上下文？

1. 在需要时才提供对应上下文
2. 注意上下文的位置
3. 减少无关的上下文

---

## 最后的话

一方面我们可以通过**提示词工程**引导 LLM "怎么答"，另一方面我们可以通过**上下文工程**缩小答案范围来引导 LLM "答什么"。

本质都是为了对抗 LLM 的随机性，把一个概率系统逐步约束成一个可控系统——这就是 Harness Engineering 的思想。
