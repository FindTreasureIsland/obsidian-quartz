## 核心内容

### 背景

作者团队使用 mono repo 管理所有端代码（接近2500 commits），除了前200个commits是Cursor半自动写的，剩下的几乎都是AI编码的squash commit。虽然会出现一些小bug，但效率提升远超这些问题。

作者认为：之后很长一段时间，工作都将是碎片化的但可并行的。

---

### Lody 支持的两种模式

1. **本地项目导入**：和开多个终端窗口一样，都在相同目录
2. **GitHub 仓库关联**：以 worktree 模式运行

**关键点**：用户不需要了解什么是 git worktree，每个新建的对话都是一个独立的工作区，不同对话之间的修改不会互相影响，但会共享 git 信息。

---

### 最佳并行开发流程

1. 创建新对话，每个对话对应一个需求或修复
2. 完成后创建 PR，PR 中可选开启 AI Review
3. 原对话中拉取 PR 评论进行多轮修复
4. 可选用 claude /simplify 进行代码优化
5. 同时进行端到端验证

---

### Skills 和 Prompts 理念

**工具理念：如无必要勿增实体**

- 只有两三个基础 skills（react-best-practices、agent-browser）
- 认为模型三个月迭代一次，每次更新都会把更多 skills 训练到基础模型中

**对 Skills 的态度**：
- Agent 对于 skills 是渐进式披露
- 先什么都不要直接去搞，遇到问题增加简单提示词去体会模型边界
- 真的干不了的事情再去添加 skills

**常用 Prompt**：
> "当前应用是未发布状态，无需后向兼容，可以做破坏性更新。"

解决 AI 经常写兼容性代码的问题。

---

### 实际工作流

**先文档再开发**
- 对于大功能和修复，先描述清楚需求
- 对话："仔细分析当前代码，将需求和解决方案详细地总结到 docs/xxx.md。我先审阅，同意后你再编码。"
- 直接点开看 AI 的 Plan，去询问或指出问题，文档迭代到符合预期后再编码
- 可以用多 Tab 开新对话让其他便宜的模型依照文档实现

**并行创建其他任务**
- 一个对话开始实现跑起来之后，继续下一个对话
- 不需要担心并行的编码会产生冲突，当做是另一个同事在同时干活
- 有冲突在所难免，但每个功能都有文档保留了意图，让 AI merge 很轻松

**PR 和 Review**
- 让 AI 创建 PR，Lody 自动关联对应 PR 并跳转 GitHub
- PR 中设置 AI Code Review，有新 commit 会自动跑 review 留下建议评论
- 但评论是没有完整此次任务 context 的 AI 做出的结论，需要把评论给到干活的那个对话判断正确性

**对话管理**
- 每个对话对应一个功能的完整生命周期
- PR 被合并时，可以将对话 Archive 掉（只是隐藏，对应工作区还保留在磁盘上）
- 真的不需要时，再到归档列表中彻底删除，释放空间

---

### 核心观点

> 很多人讨论还会不会手写代码，还会不会真的去 review 一遍 AI 写的代码。
> 
> 对于今天，真的不认为大部分人还有足够的注意力能够结合整个仓库，一行一行地看 AI 的代码到底对不对。
> 
> AI 分析和修个已知的问题不过十分钟。
