## 核心结论（先读这个）

1. **Harness 比模型更关键**：更贵的模型带来的提升很多时候没有想象中大，反而 Harness 和验证测试质量对成功率的影响更大
2. **调试优先检查工具定义**：多数工具选择错误都出在描述不准确，不在模型能力
3. **评测系统本身的问题往往比 Agent 出问题更难发现**：一直在 Agent 代码上反复调，效果未必明显
4. **先修评测，再改 Agent**

## 1. Agent Loop 的基本运转方式

Agent Loop 核心实现不到 20 行代码：感知 → 决策 → 行动 → 反馈 四个阶段不断循环，直到模型返回纯文本。

**关键设计原则**：
- 模型负责推理，外部系统负责状态和边界
- 不应该让循环体本身变成巨大的状态机
- 新能力只通过三种方式接入：扩展工具集、调整系统提示结构、把状态外化到文件或数据库

**Workflow vs Agent**：执行路径由代码预先写死的是 Workflow，由 LLM 动态决定下一步的是 Agent。核心区别在于控制权在谁手里。

**五种常见控制模式**：
1. 提示链 Prompt Chaining：顺序步骤，适合线性流程
2. 路由 Routing：分类定向，简单问题走轻量模型
3. 并行 Parallelization：分段法 + 投票法
4. 编排器-工作者 Orchestrator-Workers：中央 LLM 动态分解任务
5. 评估器-优化器 Evaluator-Optimizer：循环直到达标

## 2. 为什么 Harness 比模型更关键

Harness 包括：验收基线、执行边界、反馈信号、回退手段。

**OpenAI 的 Agent 优先开发实践**（3工程师5个月百万行代码）：
- Agent 看不到的内容等于不存在：知识必须存在于代码库本身
- 约束编码化而非文档化：进 Linter、类型系统、CI 规则
- Agent 端到端自主完成任务
- 最小化合并阻力

**任务四象限**：
- 右上角（目标明确 + 结果可自动验证）= 最适合 Agent 区域
- 左上角：任务清楚但验收靠人，吞吐量天花板是人的审查速度
- 右下角：有自动化反馈但目标模糊，会高效往错误方向跑
- 左下角：两者都缺，Agent 基本不起作用

**Harness 要做的就是把任务推进右上角。**

## 3. 上下文工程为什么决定稳定性

Context Rot：无关内容占上下文大头时，Agent 决策质量明显下滑。

**信息分层管理**：
- 常驻层：身份定义、项目约定、绝对禁止项，保持短、硬、可执行
- 按需加载：Skills 和领域知识，描述符常驻，完整内容触发时再注入
- 运行时注入：当前时间、渠道 ID、用户偏好
- 记忆层：跨会话经验写入 MEMORY.md，不直接进系统提示
- 系统层：Hooks 或代码规则处理确定性逻辑，完全不进上下文

**三种压缩策略**：
1. 滑动窗口：丢弃旧消息，成本极低，会丢早期上下文
2. LLM 摘要：成本中等，丢细节保留决策
3. 工具结果替换：占位符替换原始输出，成本极低

**Prompt Caching**：
- 精确前缀匹配才能命中，不是内容相似就触发
- 稳定的大系统提示比频繁变动的小提示实际成本更低（写入成本只付一次，后续读取折扣可达 90%）

**Skills 按需加载**：
- 系统提示只保留索引，完整知识按需加载
- Skill 描述 = 路由条件，不是功能介绍
- **反例是关键**：没有反例准确率 73%，加上反例后升到 85%
- 描述要足够短（低效约 45 tokens vs 高效约 9 tokens）

**压缩时保留优先级**：
1. 架构决策，不得摘要
2. 已修改文件和关键变更
3. 验证状态 pass/fail
4. 未解决 TODO 和回滚笔记
5. 工具输出可删，只保留 pass/fail 结论

## 4. 工具设计决定 Agent 能做什么

工具设计三阶段：
1. **API 封装**：粒度过细，Agent 要协调多个工具才能完成一个目标
2. **ACI（Agent-Computer Interface）**：工具对应 Agent 目标而非底层 API 操作
3. **Advanced Tool Use**：Tool Search + Programmatic Tool Calling + Tool Use Examples

**ACI 原则**：
- 工具边界清楚
- 参数描述直接约束格式
- 错误结构化给出修正建议

**Programmatic Tool Calling**：让模型用代码编排多个工具调用，中间结果在执行环境中流转，不进入 LLM 上下文。Token 消耗可从约 150,000 降到约 2,000。

**工具消息隔离**：框架内部事件（压缩、通知）记在会话历史里，但不应该直接进 LLM。

## 5. 记忆系统如何设计

**四种记忆**：
- 上下文窗口 = 工作记忆
- Skills = 程序性记忆
- JSONL 会话历史 = 情景记忆
- MEMORY.md = 语义记忆

**ChatGPT 四层记忆**：
1. Session Metadata：不持久化
2. User Memory（约33条关键偏好）：持久化，每次注入
3. Conversation Summary（约15个最近对话）：持久化
4. Current Session：不持久化

**整合触发回退**：
- 触发阈值：tokenUsage / maxTokens >= 0.5
- 失败路径：原始消息写入 archive/，保留完整历史

**可回退性是关键**：系统只移动指针，不删除原始消息。

## 6. 如何逐步放开 Agent 自主度

**长任务跨 session 继续**：
- Initializer Agent：只运行一次，生成 feature-list.json、init.sh、git commit、claude-progress.txt
- Coding Agent：循环执行，每次从文件系统恢复现场

**任务状态外部化**：
```json
{"tasks": [{"id": "1", "desc": "读取配置", "status": "completed"}, {"id": "2", "desc": "修改 schema", "status": "in_progress"}]}
```
约束：同一时间只能有一个 in_progress

**后台 I/O**：慢速 subprocess 放后台线程，通过通知队列在下一轮前注入结果。

## 7. 多 Agent 如何组织

**两种工作模式**：
- 指挥者模式：同步协作，人与单个 Agent 紧密互动
- 统筹者模式：异步委派，人只在起点和终点出现

**协作协议**：
- 消息结构化，有状态，append-only，崩溃可恢复
- 主 Agent 通过 JSONL inbox 协议分派任务
- 子 Agent 执行后只回传摘要，探索细节留在自己的独立上下文里

**防止幻觉放大**：交叉验证能打断错误传播链。

**顺序**：协议先定，隔离先做，再谈协作和并行。

## 8. Agent 评测应该如何做

**三组概念**：
- task 任务、trial 单次运行、grader 评分器
- transcript 完整执行记录 vs outcome 环境最终结果
- agent harness vs evaluation harness

**两个指标不能混用**：
- Pass@k：回答「Agent 理论上能不能做到」
- Pass^k：回答「已有功能有没有被改坏」

**评分器选择**：
1. 代码评分器：确定性最高，有明确答案时优先用
2. 模型评分器：需要判断语义质量时用
3. 人工评分器：建立基准，可靠但慢

**两类都要覆盖**：Agent 说「订票已完成」（transcript），vs 数据库里确实生成了订单（outcome）。

**先修评测，再改 Agent**：红色（基础设施错误率）和蓝色（模型得分）要分开看。

## 9. 如何追踪 Agent 执行过程

**Trace 需要记录**：完整 Prompt + 多轮 messages[] + 每次工具调用及返回值 + 推理链 + token 消耗 + 延迟。

**两层可观测性**：
1. 人工抽样标注：基于规则采样错误案例
2. LLM 自动评估：全量覆盖，以第一层为校准依据

**事件流做底座**：Agent Loop 在 tool_start、tool_end、turn_end 发事件，一 次发布多路消费。

## 10. OpenClaw 落地示例

**五层架构**：
1. Gateway：WebSocket 服务，统一路由
2. Channel 适配器：多渠道统一接口
3. Pi Agent：主循环、会话状态、调度
4. 工具集：shell/fs/web/browser/MCP
5. 上下文+记忆：Skills 延迟加载 + MEMORY.md

**系统提示分层叠加**：
- 平台与运行时信息
- 身份层（SOUL.md）
- 记忆层（MEMORY.md）
- Skills 层
- 运行时注入（当前时间、渠道名）

**三种触发模式**：普通会话（完整提示）、子 Agent（只带运行时信息）、heartbeat（等固定节奏唤起）。

**安全边界三件事**：谁能用 / 能在哪用 / 做了什么可追踪。

**Prompt Injection 防护**：
- 最小权限
- 敏感操作显式确认
- 标注外部内容边界
- 关键路径加独立 LLM 验证

## 11. 常见反模式

1. 系统提示当知识库 → 约定移 Skills
2. 工具数量失控 → 合并重叠，明确命名空间
3. 验证闭环缺失 → 每类任务绑验收标准
4. 多 Agent 无边界 → 明确角色权限，worktree 隔离
5. 记忆不整合 → 监控 token，超阈值自动触发
6. 没有评测 → 失败案例立刻转测试用例
7. 过早引入多 Agent → 先验证单 Agent 上限
8. 约束靠期望不靠机制 → 改用工具验证/Linter/Hook

---

## 工程实现顺序建议

1. 单渠道先跑通（Telegram → Agent → Telegram）
2. 安全边界先于功能
3. 记忆整合要早做
4. Skills 先于新工具
5. 第一个失败就建评测
